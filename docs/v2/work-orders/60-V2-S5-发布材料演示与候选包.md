# 60 V2-S5 发布材料、演示与候选包

- 开工条件：`V2-S4 ACCEPTED`。

## 3. README 必须准确说明

### 3.1 产品承诺

- UploadFit 在当前网页明确文件规则不匹配时介入，不是独立压缩器。
- 图片能力支持范围按 V1 现状描述。
- 音频只支持以人声为主的长录音转写入口；页面必须明确允许 MP3且有 maxBytes。
- S0 冻结的 MP3/WAV/M4A 精确子集，不写“支持所有音频”。
- 合规文件原样放行；音频处理有损且需要确认。

### 3.2 安装与运行

- 只粘贴 `dist/uploadfit.js` 内容，不粘贴 Markdown 围栏或源码目录。
- Tabbit 创建私有脚本、部分网址范围、保存、刷新、更新、关闭步骤。
- 生产包单 IIFE，无外部 runtime 资源。
- 记录当前验证 Tabbit 版本；不要承诺所有未来版本。

### 3.3 隐私与安全

- 文件处理在浏览器本地；音频内容不发给 AI/第三方，不持久化。
- AI 只处理与上传框关联的规则文本，并由本地校验。
- 不自动提交、付款、发布或删除。
- 有损/mono 明确确认；原文件不被覆盖。
- 官方工具、原始/无损要求、时长限制和不明确规则会停止。

### 3.4 已知限制

- 不处理音乐质量场景、视频抽音轨、批量、剪切/分段、降噪、时长墙。
- 不支持的 codec/容器清单。
- Blob Worker/WASM/CSP 和设备资源限制。
- 页面拒绝合成事件时使用下载/人工上传。
- 200MB 处理耗时与设备性能相关。

## 4. 发布候选构建

从干净依赖执行：

```powershell
npm ci
npm run check
npm run test:e2e
npm run build
npm run static-check
git diff --check
```

随后重新计算：

- `dist/uploadfit.js` raw bytes；
- SHA-256；
- 是否单 IIFE、无 import/export；
- runtime external dependencies=0；
- 依赖许可文件存在。

同一 SHA 写入 README 发布清单、S5 handoff、证据 JSON 和最终验收输入。

## 5. 安装、更新和关闭验证

在真实 Tabbit：

1. 新建私有临时脚本并粘贴最终候选；
2. 仅匹配非敏感测试网址；
3. 保存、刷新，确认一个 host/session；
4. 用小型音频核心场景和图片场景各执行一次；
5. 用同一脚本位置粘贴相同/更新候选，确认没有重复安装；
6. 关闭自动运行并保存，刷新确认不复活；
7. 关闭临时页，不公开分享。

若用户授权正式公开分享，另记录公开链接/可见性，但不得把脚本 ID、账号或私有链接提交仓库。没有授权时只交付候选包和明确的待用户操作清单。

## 6. 三分钟演示脚本

推荐结构：

```text
0:00–0:20  最后一公里：网页上传规则挡住文件
0:20–0:55  图片能力简短回顾（已验收）
0:55–1:20  长语音转写页读取 MP3 + 100MB 规则
1:20–1:50  展示 200MB 录音、目标码率/大小、明确有损/mono 确认
1:50–2:20  用较小代表 fixture 现场演示进度、处理、复检、回填
2:20–2:35  展示真实 200MB→100MB 的结构化实测证据，不剪辑冒充实时完成
2:35–2:50  隐私：外部请求 0、AI 不接触音频、不自动提交
2:50–3:00  边界：时长墙/官方工具/不明确规则会停止
```

若 200MB 实时处理无法在演示时限内完成，必须明确说“这是此前同候选 SHA 的完整实测结果”，不能用快进或预制文件伪装实时速度。

## 7. 最终文档一致性

核对：

- 产品支持子集与 S0 ADR 一致；
- 所有测试数量、Tabbit 版本、bytes/SHA 一致；
- 体积写 raw JS，不写 gzip 冒充；
- 200MB/100MB 明确使用 decimal bytes 还是 MiB；核心证据使用精确 bytes；
- 不出现“无损音频压缩”“支持所有网站/格式”“保证转写准确率”；
- V1 归档状态和 V2 当前状态清晰。
