# 30 V2-S2 音频规划、流式处理与复检

## 3. 施工步骤

### S2.1 纯函数码率规划

实现共享契约中的计划函数，输入只包含安全元数据、RuleSet 和选项，输出 AudioProcessingPlan。

计算顺序：

1. 校验页面明确允许 `audio/mpeg`/`.mp3`；
2. 校验 `maxBytes` 有限、为正且大于最小容器预算；
3. 合规文件返回 `passthrough: true`；
4. 计算 `safeTargetBytes = min(floor(maxBytes * 0.95), maxBytes - 64KiB)`；
5. 用有限 `durationSeconds` 和容器保留量计算 raw bitrate；
6. 从 `[320,256,224,192,160,128,112,96,80,64,56,48]` 选择不超过 raw 值的最高档；
7. 默认保留源声道；只有保留双声道不满足质量策略时提出 mono；
8. 添加 `AUDIO_LOSSY_TRANSCODE`，必要时添加 `AUDIO_DOWNMIX_MONO`；
9. 估算输出区间，固定 encodePassLimit=2；
10. 无 48kbps 可选项时返回 `AUDIO_TARGET_UNSAFE`。

所有数学输入先做 `Number.isFinite`、范围和溢出检查。不得产生负数、Infinity、NaN 或高于页面上限的估算。

### S2.2 确认解析

实现与图片 confirmation 等价的不可变更新：

- 只接受当前 plan 中存在的 confirmation id/type；
- 拒绝伪造、重复、过期或 payload 改参数；
- UI 只能接受/拒绝，不能传入自选低码率绕过 planner；
- 任一必要确认未解决时 `executable: false`；
- 用户拒绝后不产生处理调用；
- 新文件/新规则必须创建新 confirmation。

### S2.3 Worker 运行时

按 S0 已验证原型整理为 production 模块：

- Worker 源码内联到单 IIFE，使用 Blob URL 启动；
- START/CANCEL/DISPOSE 与 taskId 严格匹配；
- 读取、demux、decode、downmix/resample、encode、finalize 分阶段；
- progress 限流，不超过每 100ms 一次；
- 错误映射到稳定 error code；
- 完成、取消和错误都走统一 cleanup；
- Worker 不能访问 DOM、网络、持久化或 Tabbit provider；
- 不把原始异常对象、文件名、帧数据发回主线程。

如果选定编码器 API 天然要求主线程或完整 PCM，说明 S0 契约失效，应停止并报告，不能自行退化。

### S2.4 流式 pipeline

实现 `processAudio(file, plan, options)`：

- 校验 `plan.executable`、确认已解决、File 类型和 AbortSignal；
- 同时只允许一个 pipeline 实例；
- 输入块、PCM 和输出 chunk 有界；
- 接收 onProgress，异常回调不能破坏处理；
- 用户 abort 时发 CANCEL，并在 1 秒截止后强制 terminate；
- 第一次输出先 inspect + validate；
- 如果 `safeTargetBytes < output.size <= maxBytes`，可以通过并 warning，不编码第三次；
- 如果 `output.size > maxBytes`，降一个阶梯，且仍不低于 48kbps，执行第二次；
- 第二次仍超限返回 `AUDIO_OUTPUT_TOO_LARGE`；
- 失败时不返回半成品 File，不保留 Blob URL；
- 成功生成新的 `File(..., {type:'audio/mpeg'})`，不覆盖原对象。

注意：第二次处理可以重新读取原 File，但仍须流式和可取消。不得缓存第一次完整 PCM 来换速度。

### S2.5 最终复检

最终验证与编码器分离，至少检查：

- MP3 帧签名和容器；
- `File.type === 'audio/mpeg'`；
- `0 < size <= rules.maxBytes`；
- duration 有限且与源时长在容器/尾帧容差内，不允许意外截短；
- sampleRate/channels 符合 plan；
- 能解析首、中、尾部的代表性帧或执行选定解码抽检；
- 输出不存在只含标签无音频帧的空壳；
- validation.valid 才能组成成功 result。

不要求逐 PCM 位相等，但必须证明时长未被语义裁剪。

### S2.6 MediaHandler 包装

实现 audio handler：

```js
supports -> inspect -> validate -> plan -> resolveConfirmation
-> process -> validateOutput -> dispose
```

用轻量 image adapter 验证 core registry 可同时注册 image/audio；不得重写既有 image pipeline。未知 mediaKind 返回通用 unsupported，不猜测。

### S2.7 资源统计与清理

ProcessResult/诊断记录：

- inputBytesRead、outputBytes、encodePasses、durationMs；
- workerUsed 必须为 true；
- peakBufferedBytes 可获得时记录，不能获得时为 null 并用 chunk/队列上界证明；
- 完成/失败/取消的 Worker terminated、object URL revoked、队列清空；
- 处理后运行第二个任务不继承首任务状态。

## 4. 单元测试 Must

### 4.1 Planner 边界

- 200,000,001→100,000,000 的 safe target 和离散码率；
- decimal MB 与 MiB 已由规则层转换后的字节；
- 极短/极长 duration、零/NaN/Infinity；
- maxBytes 过小、64KiB reserve 边界；
- raw bitrate 正好位于每个阶梯上下；
- 48kbps 可行/不可行分界；
- stereo 保留和 mono confirmation；
- compliant passthrough；MP3 不允许；max 缺失；
- plan 输入不被 mutate。

### 4.2 Confirmation

- accept/decline、重复、伪造 id/type、过期 plan；
- lossy + mono 两个确认必须全部通过；
- payload 不能修改 bitrate/channel/maxBytes。

### 4.3 Output validator

- 正确 MP3；错误 MIME；伪 MP3；零字节；超限；截断；时长显著丢失；计划声道不符。

## 5. 集成测试 Must

- 每个 S0 支持输入子集到 MP3 的小 fixture 成功；
- 超限 MP3 重新编码；WAV/M4A 转码；
- 第一遍在 max 内成功；第一遍超限、第二遍成功；两遍仍失败；
- progress 单调、0–1、有节流；
- processing 中 abort，1 秒内结束；
- Worker 初始化失败、解码失败、编码失败和输出复检失败；
- input 被重复处理、并发任务被拒绝/排队；
- 完成/失败/取消资源清理；
- 短 fixture 快速套件 + 不入 Git 的大 fixture 手动/慢速套件。

大文件测试应能通过环境变量或明确脚本启用，普通 `npm run check` 不每次生成 200MB；但阶段验收必须执行一次并保存结构化结果。

## 6. 性能与内存验收

- 实际 200MB fixture 使用 production-equivalent worker handler 处理；
- 输出 ≤100,000,000 bytes；
- 主线程 100ms 心跳最大间隔目标 ≤500ms；
- 不出现与时长成比例增长的 PCM 常驻集合；
- chunk/queue 实际峰值或理论硬上界写入证据；
- 中途取消在 1 秒内停止；
- 处理后可再次运行小文件，无 Worker/内存残留异常。
