# 30 S2：图像处理引擎

## 1. 阶段使命

实现从 `File + RuleSet` 到 `ProcessResult` 的纯本地图像管线：读取真实元数据、校验、生成处理计划、方向修正、转码、缩放、压缩、复检。该模块不接触网页 DOM、Tabbit AI、任务状态机或正式 UI。

S2 与 S1 可并行。任何需要用户决定的操作只生成 confirmation，不可在图像模块里默认同意。

## 2. 前置条件

- S0 核心闸门已通过。
- 共享契约、配置常量和错误码可导入。
- Canvas、toBlob、createImageBitmap/HTMLImageElement 的实测能力结论已记录。

## 5. 元数据和输入防护

### 5.1 处理前拒绝

- `file.size > 50 MiB` → `FILE_TOO_LARGE_TO_PROCESS`。
- 宽或高 >20,000 → `PIXEL_LIMIT_EXCEEDED`。
- 解码后像素 >80MP → `PIXEL_LIMIT_EXCEEDED`。
- 空文件、损坏文件 → `DECODE_FAILED`。
- 非 JPG/JPEG、PNG、WebP → `UNSUPPORTED_FORMAT`。

先检查字节和文件签名，再进行高成本解码。捕获浏览器内存/Canvas 上限，转为稳定错误码，不让未处理异常逃逸。

### 5.2 MIME真实性

除 `file.type` 和扩展名外，最少检查：

- JPEG SOI。
- PNG 固定签名。
- WebP 的 RIFF/WEBP 标记。

签名、MIME、扩展名不一致时记录 violation；输出必须让真实编码、MIME 和扩展名一致。不得只改扩展名。

### 5.3 EXIF

- 使用包含 orientation 6 的 fixture 验证浏览器解码行为。
- 若原生已自动旋转，不能重复旋转。
- 若 Tabbit/测试浏览器行为不一致，实现最小 EXIF orientation 解析器。
- 输出重新编码后方向归一，不保留 GPS 等无关元数据。

## 6. 校验和计划

### 6.1 合规文件

`validateFile` 返回 `valid=true` 时 controller 将原样放行。图像模块不得为了“优化”重编码、重命名或改变元数据。

### 6.2 处理顺序

计划固定为：

```text
DECODE → ORIENT → FORMAT → DIMENSION/CROP → CONFIRM
→ DRAW → ENCODE → SIZE_OPTIMIZE → FINAL_VALIDATE → NEW_FILE
```

### 6.3 格式选择

1. 当前格式合法且可满足大小：保持。
2. 当前格式不合法：从允许白名单选择。
3. 多格式允许：不透明照片优先 JPEG；透明图/线稿优先 PNG；WebP 仅页面明确允许。
4. 透明 PNG → JPEG 必须添加 `FLATTEN_BACKGROUND` confirmation，默认白底预览。
5. 不自动改变蓝/红/白证件照背景内容。

### 6.4 尺寸和比例

- exact：比例误差 ≤1.5% 等比缩放；>1.5% 生成固定比例 crop confirmation。
- max：超限才等比缩小，未超限先保持。
- min：不足时生成 upscale confirmation；页面禁止放大则 unfixable。
- ratio only：不匹配生成 crop confirmation。
- 禁止拉伸。
- 精确宽高不能通过后续继续缩尺寸满足体积。

`planner` 只计算裁剪框/目标和确认项。实现纯函数 `resolveProcessingConfirmation(plan, confirmation)`，按共享契约验证 id/type/payload 并返回新计划。没有用户确认的 crop/flatten/upscale 不得进入 `processImage`；如调用方强行传未确认计划，返回 `USER_CONFIRMATION_REQUIRED` 或使 `executable=false`，不得静默执行。

## 7. Canvas 和编码

- `imageSmoothingEnabled=true`、`imageSmoothingQuality="high"`。
- 大幅缩小可分级绘制，需有上限，及时释放中间 canvas。
- 透明转 JPEG 前白色填充。
- Canvas 不插入业务 DOM。
- 首选 `canvas.toBlob`/OffscreenCanvas `convertToBlob`，不把 Base64 作为长期中间格式或日志。
- 编码失败/空 Blob 视为 `PROCESSING_FAILED`。

### 7.1 最大体积

- `targetMax=floor(maxBytes × 0.90)`。
- JPEG/WebP 在 0.45–0.95 中二分，最多 8 次。
- 选择不超过 targetMax 的最高可用质量。
- 最低质量仍超限且尺寸可变：

```text
scale = sqrt(targetMax / currentBytes) × 0.95
```

- 单轮 scale 限制 0.5–0.95，最多 3 轮，不突破最小尺寸。

### 7.2 同时有最小和最大体积

- 在合法区间选尽可能高质量。
- 低于 min 时提高质量或选择合法且更低压缩率的格式。
- 禁止加垃圾字节、随机噪点或无意义元数据“凑体积”。
- 仍不足/超限就失败并返回清晰 violation。

### 7.3 PNG

- 不使用 JPEG quality 参数假装控制 PNG。
- 页面允许 JPEG 且为不透明照片时可以计划转 JPEG。
- 只允许 PNG 且过大时，仅在尺寸规则允许下缩小。
- MVP 不引入 PNG 量化 WASM；不能满足就诚实失败。

## 8. 输出文件

- 命名：`原名_uploadfit.目标扩展名`。
- 去除重复 `_uploadfit`，非法字符过滤，最长 120 字符。
- 不从页面拼姓名、身份证号。
- 创建 `File` 后重新检查真实 MIME/签名、扩展名、字节、解码宽高、比例、非空和可解码。
- 复检不通过返回 `OUTPUT_VALIDATION_FAILED`，`ProcessResult.file` 不得交给注入器。

## 9. Worker 策略

| 能力 | 行为 |
|---|---|
| Worker+OffscreenCanvas | 可在 Worker 处理 |
| Worker 无 OffscreenCanvas | 主线程 Canvas，不强行拆分 |
| Blob Worker 被 CSP 阻止 | 捕获后主线程重试一次 |
| createImageBitmap 不可用 | HTMLImageElement+object URL |

- 单脚本通过内联函数构造 Blob Worker。
- Worker 完成/异常/取消后 terminate 并 revoke URL。
- 主线程长操作要让出事件循环或报告进度；4000×3000 常规照片不得连续冻结 >500ms。
- Worker 与主线程必须产生等价 `ProcessResult`。

## 10. Fixture 基线

必须准备非敏感样本：

1. 约 2MB、1170×1701 PNG。
2. 约 500KB、390×567 JPEG。
3. 约 20KB、390×567 JPEG。
4. 约 5MB、4000×3000 JPEG。
5. EXIF orientation 6 手机方向样本。
6. 透明 PNG。
7. 损坏图片。
8. WebP。
9. 80MP 边界通过生成器构造，不在仓库存巨大二进制。

可以程序生成的 fixture 必须可复现并记录生成命令；不得使用个人证件照。

| ID | 场景 | 预期 |

## 12. 阶段退出标准

- 公共函数 `inspectImage`、`validateFile`、`createProcessingPlan`、`resolveProcessingConfirmation`、`processImage` 契约稳定。
- I01–I18 全部通过。
- 合规文件路径能证明未重新编码。
- 三类有损操作在未确认状态下无法执行。
- 输出未通过复检时绝不返回可注入成功结果。
- Worker/CSP/createImageBitmap 失败均有主线程/HTMLImageElement 降级证据。
- 常规 4000×3000、≤10MB 照片在参考 PC 总处理 ≤5秒；连续冻结 ≤500ms。
- 对象 URL、Worker、Canvas 引用均有清理测试或证据。
- 交接文档记录 fixtures、性能环境、失败边界和已知色彩/编码差异。

## 13. 禁止事项

- 不读取或修改网页 DOM。
- 不调用 AI，不上传文件，不使用运行时 CDN/WASM。
- 不静默 crop、flatten 或 upscale。
- 不加垃圾数据凑最小体积。
- 不声称控制了 DPI 元数据；DPI 只展示。
- 不为绕过错误把复检关掉或放宽规则。
