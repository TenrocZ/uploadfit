# 40 S3：任务编排与上传闭环

## 1. 阶段使命

把 S0 的注入器、S1 的规则引擎和 S2 的图像引擎连接成可控状态机，完成：

```text
发现上传器 → 文件选择 → 预检/放行 → 本地处理
→ 最终复检 → 回填 → 明确拒收兜底 → 最多一次重试
```

本阶段使用最小可替换 view adapter 展示状态，不制作正式视觉和裁剪器；用户确认可由测试 stub 驱动，正式 UI 由 S4 接入。

## 2. 前置条件

- S0、S1、S2 均为 `READY_FOR_ACCEPTANCE`。
- 三个阶段的 handoff、测试和接口变更已核对。
- `npm test -- --run` 和 `npm run build` 基线为绿色。
- S2 的 confirmation 机制能阻止未确认有损处理。

## 3. 文件范围

- `src/core/session.js`、`state-machine.js`、`task-controller.js`、`cleanup.js`。
- `src/dom/rejection-observer.js`。
- `src/adapters/registry.js`。
- 必要的 `src/bootstrap.js` 集成改动。
- `tests/unit/state-machine.test.js`、`rejection-classifier.test.js`。
- `tests/integration/task-controller.test.js`、`upload-loop.test.js`、`cleanup.test.js`。

- `docs/handoffs/S3-handoff.md`、`docs/evidence/S3/*`。

不得实现正式 UI 视觉、真实 Tabbit AI provider 或发布材料。

## 5. Controller 边界

`TaskController` 是唯一跨模块编排者。建议最小接口：

```js
class TaskController {
  start();
  registerUploader(uploaderContext);
  handleFileChange(event, uploaderContext);
  confirmTask(taskId, confirmationPayload);
  cancelTask(taskId);
  restoreTask(taskId);
  subscribe(listener);
  getSnapshot();
  dispose();
}
```

UI 或测试 view 只能调用这些用户意图方法；不得直接调用 image/injection 产生副作用。

Snapshot 只包含可展示数据，不能暴露 File、input 元素、图片像素或完整页面文本：

```js
{
  sessionState: "ARMED",
  uploaderCount: 1,
  activeTask: {
    taskId: "...",
    status: "INSPECTING",
    label: "证件照",
    current: { mime: "image/png", size: 2800000, width: 1170, height: 1701 },
    rules: {},
    plan: null,
    result: null,
    errorCode: null
  }
}
```

## 6. 文件选择分流

捕获阶段监听 input 的 `change`：

1. 先检查 injectionGuard；命中一次性令牌则只让网站处理，不创建新任务。
2. 读取当前 `input.files`；0 个文件直接返回。
3. `multiple=true` 且本次 >1 个：提示暂不支持批量，不修改集合，不启动处理。
4. 建立随机 taskId，保留原 File 引用，仅在本页内存。
5. 获取/刷新 RuleSet，检查文件元数据。
6. 按下表分流。

| 条件 | 事件行为 | 状态/后续 |
|---|---|---|
| 规则明确且 confidence≥0.90，文件合规 | 完全不拦截 | PASSTHROUGH→ARMED |
| 规则明确且不合规、仅安全自动修复 | `stopImmediatePropagation()`；`preventDefault()` 仅辅助 | PROCESSING |
| 规则明确但需 crop/flatten/upscale | 阻断原网站处理 | NEEDS_CONFIRMATION |
| confidence 0.75–0.89 | 阻断前必须展示规则确认；用户选原文件则透传 | NEEDS_CONFIRMATION |
| confidence<0.75 或没有可执行规则 | 完全不拦截 | WAITING_REJECTION |
| 不可修复/官方工具/冲突 | 默认不修改；给安全解释 | STOPPED |

说明：

- 捕获监听器仍可能晚于网站更早注册的 document 捕获监听器，不能声称覆盖所有站点。
- 不替换原 input 节点。
- 合规文件不重新注入。
- 用户选择“使用原文件”时，若原事件已经被阻断，应通过恢复原文件并提示用户重新选择/继续网页原流程；不得自动提交。

## 7. 任务队列与并发

- 每个 input 有独立 UploaderContext 和最近任务。
- 同时只允许一个 `PROCESSING/INJECTING`；其余任务 FIFO 等待。
- 新用户选择同一 input 时，旧的未处理任务应取消并清理，不能稍后覆盖新文件。
- 页面导航、input 移除或 session dispose 要 abort 当前异步工作。
- 所有异步完成回调先检查 task 是否仍活跃，避免过期结果注入。
- 文件名不能作为去重或关联依据。

## 8. 拒收观察器

### 8.1 窗口和范围

- 文件选择后、规则不足或注入后需要监听页面反馈时启动 30 秒窗口。
- 优先观察 input 祖先、`aria-describedby`、附近错误容器、`role=alert`、`aria-live`。
- MutationObserver 只处理新增或文本变化节点，100ms 合并。
- 成功、超时、导航、取消、dispose 后停止；stop 函数幂等。
- 不 patch `fetch`/`XMLHttpRequest`，不读取请求/响应。

### 8.2 关联优先级

1. 错误节点在上传器祖先容器内。
2. `aria-describedby` 显式关联。
3. DOM 距离较近。
4. 文件选择后出现的全局 toast。
5. 仅有一个活跃任务时允许弱关联。

多个活跃任务且无法确定归属时，记录 `AMBIGUOUS_REJECTION_ASSOCIATION` 并停止自动处理。

### 8.3 明确拒收

必须同时满足：

- 与最近上传在时间和 DOM 上相关。
- 含文件/图片/照片/格式/大小/像素/尺寸/宽高/比例语义。
- S1 能提取至少一条结构化强制规则。
- 不含网络、系统、权限、登录、内容审核、清晰度、身份不一致或官方工具语义。
- 当前任务未自动重试。

明确拒收候选按 `rejection` 高优先级与现有规则合并，冲突仍需显示。合并后重新 inspect/validate/plan，不可直接“压一下”。

### 8.4 模糊拒收

“上传失败、系统繁忙、文件不合法、未知错误”等：

- 不改文件。
- 不重试。
- 转 `STOPPED`。
- 错误码和文案说明“未识别到可安全修复的文件规格问题”。

## 9. 处理、确认和注入

### 9.1 处理

- `ProcessingPlan.executable=true` 才可调用 `processImage`。
- 每个进度回调必须绑定 taskId，过期任务不更新 snapshot。
- 处理后再次检查 `result.validation.valid` 和 `result.file instanceof File`。
- 失败转 STOPPED；不得注入部分结果。

### 9.2 确认

Controller 等待 S4/UI 或测试 stub 的明确操作：

- crop payload 必须包含合法、边界内的归一化裁剪矩形。
- flatten 确认明确白底。
- upscale 确认后仍附带“像素达标不等于审核通过”warning。
- controller 通过 S2 的 `resolveProcessingConfirmation` 生成新计划，不直接篡改 confirmation 或把 `executable` 强制设为 true。
- Esc/取消不处理、不注入。
- 低置信规则确认与有损操作确认是两类独立确认，不可一次模糊同意全部。

### 9.3 注入

- 只调用 S0 的 `injectFile`。
- 写入前 input 必须仍在 DOM 且属于当前 uploader。
- 成功写入后才记录 `INJECTION_COMPLETED`。
- `input.files` 写入失败时提供 download fallback 状态。
- `isTrusted=false` 网站不响应时，提示用户使用网页原按钮或下载重选。

## 10. 自动重试语义

自动重试仅是再次分发 input/change，让网页自己的自动上传逻辑运行，不是 click。

必须全部成立：

- 当前规则来自本次明确拒收，或本次注入后又收到明确拒收并转为 rejection source。
- adapter 明确返回选择即上传；或 generic 路径已经观察到“用户未点击任何业务按钮，仅文件 change 后就在30秒窗口内出现与该 input 关联的明确拒收”。除此之外 generic 一律按表单型处理。
- 输出最终复检通过。
- `retryCount===0`。
- 原 input 仍连接。
- 用户未取消，session 未 dispose。
- 不涉及保存、下一步、提交、发布、付款等最终行为。

在分发重试事件之前执行 `retryCount += 1`。后续任何拒收都转 STOPPED，不再处理。表单型页面只显示“文件已适配，请继续使用页面原按钮”。

不得仅根据页面上存在“上传/保存/提交”文字猜测自动上传，也不得为了探测而点击按钮。测试页需记录从原始 change 到拒收之间的业务 click 次数为0，作为 generic 自动上传判断证据。

## 12. 闭环集成测试

| ID | 场景 | 必须断言 |
|---|---|---|
| L01 | 明确规则预检 | 不合规 PNG 被处理、复检、回填；网页只收到新文件 |
| L02 | 完全合规 | 原对象/原事件继续，无编码/注入 |
| L03 | 初始无完整规则→明确拒收 | 新规则合并、处理、只重试一次 |
| L04 | 重试仍拒收 | STOPPED；事件计数不再增加 |
| L05 | 模糊错误 | 文件不变、retry=0、process 未调用 |
| L06 | 表单型 | 文件被替换，但任何 button click 计数为0 |
| L07 | 两个 uploader | 规则、错误和任务不串线 |
| L08 | 同一 input 快速选择两次 | 旧任务取消，最终只注入第二个结果 |
| L09 | multiple 两文件 | 不修改集合、不启动处理 |
| L10 | DataTransfer失败 | download/manual fallback，不能报上传成功 |
| L11 | 恢复原文件 | 原 File 回填，仍不点击按钮 |
| L12 | 页面关闭/导航 | observer、队列、监听和异步任务全部清理 |

## 13. 阶段退出标准

- C01–C12、L01–L12 全部通过。
- 状态变化、日志事件和错误码与共享契约一致。
- 合规透传、规则不足透传、明确不合规拦截三条事件策略有自动测试。
- 选择即上传仅重试一次；表单型 click 计数始终为 0。
- 模糊错误、冲突规则、官方工具要求从不进入 process。
- 同时多任务的内存/顺序受控，过期异步结果不能覆盖新选择。
- dispose 后无 DOM 观察、事件响应、Worker 或 object URL 残留。
- 交接提供测试页录屏/截图、事件计数、状态轨迹和诊断 JSON。

## 14. 禁止事项

- 不在 controller 中复制规则或图像算法。
- 不把注入成功等同于服务端上传成功。
- 不通过 click 模拟任何网页业务按钮。
- 不无限观察/重试，不吞掉第二次拒收。
- 不修改其他表单字段，不读取网络请求体。
- 不让测试 stub 用户确认进入生产构建。
